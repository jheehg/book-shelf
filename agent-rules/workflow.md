# Git 작업 규칙

## 브랜치

- `main`은 항상 배포 가능한 상태로 둔다. 빌드와 관련 테스트가 통과해야 한다.
- 구현 작업은 목적이 분명한 브랜치에서 시작한다. 이름은 `feat/<주제>`, `fix/<주제>`, `docs/<주제>`, `chore/<주제>`를 사용한다.
- 하나의 브랜치는 하나의 목적만 가진다. 구현 코드, 해당 테스트, 필요한 Flyway 마이그레이션을 함께 둔다.
- 개인 프로젝트이므로 PR은 만들지 않는다. 검증한 브랜치를 `main`에 병합하는 일은 사용자가 요청할 때만 한다.

## 작업 트리

- 수정 전에 `git status --short`를 확인한다. 사용자와 관계없는 변경은 보존하고 덮어쓰지 않는다.
- 사용자가 명시적으로 요청하지 않았다면 `reset --hard`, `checkout --` 같은 파괴적인 Git 명령은 사용하지 않는다.
- `README.md`, `agent-rules/`처럼 오래 유지할 프로젝트 문서는 작업 범위에 포함될 때 버전 관리한다. 세션 중간 메모나 비공개 자료는 기본으로 추가하지 않는다.

## 커밋과 푸시

- 모든 커밋 전에 정확한 파일 경로, 제안하는 커밋 메시지, 검증 결과를 보여주고 사용자의 허가를 받는다.
- 스테이징은 파일 경로를 명시한다. `git add .`, `git add -A`는 사용하지 않는다.
- 커밋 메시지는 `feat:`, `fix:`, `docs:`, `chore:` 같은 Conventional Commit 형식의 접두사를 사용한다. `Co-Authored-By`, `Claude-Session`, `Signed-off-by` 등 어떤 트레일러도 붙이지 않는다.
- `.env`, 실제 자격 증명, 토큰, 개인 키는 절대 커밋하지 않는다. 커밋 전 스테이징된 내용에 비밀값이 섞이지 않았는지 확인한다.
- 커밋 허가는 푸시 허가가 아니다. 푸시는 사용자가 명시적으로 요청할 때만 한다.

## 검증

- 변경 범위에 맞춰 검증한다. 서버 동작을 바꾸면 구체적인 환경 문제가 없는 한 관련 테스트와 `./gradlew test`를 실행한다.
- 문서만 바꿨다면 `git diff --check`를 실행한다.
- 커밋을 제안하기 전에 실행한 명령, 결과, 남은 제약을 보고한다.
