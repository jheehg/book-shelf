# book-shelf — 바코드로 3초에 기록하는 서재

작성일: 2026-09-27
개정: 2026-09-30 — 알라딘 OpenAPI 종료(2026-10-30)와 네이버 책·쇼핑 검색 API 종료(2026-07-31)로 외부 제공자를 다시 설계했다. 실측 근거는 `docs/notes/providers.md`. 같은 날 독립 리뷰 16건을 반영했다
기간: 2026년 10월 ~ 12월 (약 14주, 주말 4~5시간)

## 1. 배경과 목표

### 출발점
- `spring-study`(주문·결제 API) 하반부와 **병행**한다. 그쪽은 주 9~14시간을 이미 쓰고 있다
- 프론트엔드 경험이 많지만(React/Next/Svelte/WebRTC), **프론트에 치우치지 않은 풀스택**을 경험하고 싶다
- 기존에 해본 것 말고 **폭을 넓히는** 쪽을 원한다
- **실제로 배포되어 불특정 다수가 쓰는 서비스**까지 가는 것이 목표다. 포트폴리오로도 쓴다

### 이 프로젝트로 얻으려는 것
1. **모바일 앱** — Flutter/Dart라는 새 언어·새 런타임
2. **예산에서 역산하는 설계** — 외부 API 일일 호출 제한이 캐시 구조를 강제한다
3. **인증 없는 공개 경로의 보안** — 실수 한 번이 전체 유출이 되는 영역
4. **앱과 서버, 두 배포 주기를 동시에 운영하는 경험**
5. **외부 제공자가 사라지는 것을 전제로 한 설계** — 이 문서를 쓰는 동안 실제로 두 곳이 닫혔다 (6장)

### 이 문서가 정하지 않는 것
구현 순서와 주차별 과제의 세부는 별도 구현 계획에서 다룬다.

### 이 문서의 표기
**(가정)**이 붙은 서술은 아직 실측하지 않은 것이다. 실측 결과가 다르면 그 서술과 그것에 기댄 설계를 함께 고친다. 실측 마감과 불합격 기준은 6-7절에 있다.

## 2. 만들 것

**바코드를 찍으면 3초에 기록되는 서재.** 찍는 순간 **"이 책을 어떻게 읽을 수 있는가"** — 동네 도서관에서 빌릴 수 있는지, 새 책으로 살 수 있는지, 중고·전자책은 어디서 보는지 — 를 한 화면에 답한다.

```
[Flutter 앱]  ──JSON──▶ ┌──────────────┐ ──HTTP──▶ 카카오 책 검색    책 정보·검색·새 책 상태 (상업)
  스캔·검색·기록         │  Spring Boot │ ──HTTP──▶ 도서관 정보나루   빌리기 (공공)
                         │              │ ──HTTP──▶ Google Books      전자책 가격 (상업)
[브라우저]   ◀──HTML──── └──────────────┘ ──SQL──▶  PostgreSQL
  공개 서재·책 페이지                      서점·중고·전자책 서점은 API 없이 링크만
  (비로그인, SEO)
```

### 왜 이 아이템인가

독서 기록 앱은 포화 시장이다(왓챠피디아, 플라이북, 리디·알라딘 책장). 기능 개수로는 이길 수 없다. 이기는 지점은 둘뿐이며, **설계 내내 이 두 기준으로 기능을 쳐낸다.**

1. **기록 비용이 0에 수렴한다** — 노션에 책을 기록하려면 제목 치고 표지 찾고 링크 붙이느라 3분이 걸린다. 바코드 한 번이면 3초다. 기록이 비용이 아니라 보상이 된다
2. **그 자리에서 "어떻게 읽을까"에 답한다** — 사람마다 쓰는 서점이 다르고, 사지 않고 빌리는 사람도 많다. 도서관 대출 가능 여부와 판매 상태, 그리고 모든 구매처로 가는 길을 한 화면에 모으는 서비스는 흔하지 않다

이 둘이 빠지면 왓챠피디아 열화판이 된다.

### 2-1. 읽을 수단 한 화면

| 칸 | 보여주는 것 | 출처 | 기준 시각 |
|---|---|---|---|
| **빌리기** | 내가 등록한 도서관(최대 3곳)마다 대출 가능 / 대출 중 / 미소장 (`bookExist`의 `hasBook`·`loanAvailable` 두 값에서 옮긴다) | 정보나루 | "전날 기준" (정보나루가 조회일 기준 전날 대출 상태를 준다) |
| **새 책** | 판매 중 / 주문 후 발송 / 판매 정보 없음, 정가·판매가 | 카카오 | "N시간 전 기준" |
| | [교보문고] [예스24] [알라딘] [영풍문고] | 링크만 | — |
| **중고** | [알라딘 중고] [예스24 중고] | 링크만 | — |
| **전자책·구독** | Google Play 도서 가격 — **같은 책 확인**을 통과할 때만, "powered by Google"과 함께 | Google Books | "N시간 전 기준" |
| | [Google Play 도서] [리디] [교보eBook] [밀리의서재] | 링크만 | — |

**표시 규칙**
1. **상태가 있는 칸에만 기준 시각을 붙인다.** 링크 칸은 상태를 흉내 내지 않는다
2. **링크는 "그 서점에서 이 책 검색하기"다.** 그 서점에 책이 없을 수 있으므로 "여기서 판다"고 말하지 않는다
3. **제공자가 죽어도 화면은 비지 않는다.** 카카오가 죽으면 새 책 칸이 "가격 확인 불가"가 되어도 링크는 남는다. 링크는 API가 필요 없어 항상 동작한다
4. **판매 상태를 부풀리지 않는다.** 카카오 `status`가 빈 값이면 "판매 정보 없음"이다 — 절판이라고 단정하지 않는다
5. **가격이 없으면 숫자를 쓰지 않는다.** 카카오 `sale_price = -1`이거나 `price = 0`이면 그 값은 없는 것으로 저장한다(실측 487건 중 154건). "-1원"·"0원"을 화면에 쓰지 않는다
6. 서점 링크 형식은 설정 한 곳에 둔다. 종이책 서점은 `{isbn}`, 전자책 서점은 `{title} {author}`로 만든다 — 전자책은 ISBN이 종이책과 달라 종이책 ISBN으로는 검색되지 않는다(실측)

**같은 책 확인 (Google Play 가격)**

Google Books는 종이책 ISBN으로 전자책을 찾지 못해 제목+저자로 검색하는데, 번역본·다른 언어판·다른 권이 섞인다(실측: 중국어판, 타밀어판, 토지 1권 검색에 7·14·18권). **틀린 숫자보다 숫자 없음이 낫다.** 아래 조건을 **모두** 만족할 때만 가격을 보여주고, 아니면 링크만 둔다.

1. **언어를 먼저 판단한다.** 책의 언어는 ISBN 국가 번호로 정한다: 978-89·979-11 → `ko`, 978-0·978-1 → `en`. **그 밖의 ISBN이면 Google을 부르지 않는다**(어차피 가격을 표시하지 않는다). Google 결과의 `volumeInfo.language`가 같아야 한다 **(가정 — 이 필드의 정확도는 W1에 오탐 사례로 확인)**
2. **제목이 같다.** 양쪽 제목을 정규화해 비교한다: NFC → 소문자 → `:` 뒤 부제 제거 → 괄호와 그 안 내용 제거 → 문장부호·공백 제거
3. **권 표시가 같다.** 정규화 **전에** 양쪽 제목에서 권 표시를 뽑아 비교한다. 권 표시는 괄호 안이나 제목 끝의 숫자, `N권`, `N부`, `N편`, `상`·`중`·`하`다. 한쪽에만 있거나 값이 다르면 탈락이다(둘 다 없으면 통과)
4. **저자가 같다.** 카카오 `authors`의 **첫 번째** 이름을 정규화(공백 제거, 소문자, 끝의 `외` 제거)한 값이 Google `authors` 중 하나를 같은 방식으로 정규화한 값과 **완전히 같아야** 한다. 역자(`translators`)는 보지 않는다. 표기가 다른 이름("한강"/"Han Kang")은 다른 저자로 본다 — 놓치는 쪽이 틀리는 쪽보다 낫다
5. **후보가 정확히 하나다.** 통과한 후보를 전자책 ISBN(없으면 Google volume id)으로 중복 제거한 뒤 **정확히 하나일 때만** 표시한다. 둘 이상이면(원판과 개정판 가격이 다르면) 표시하지 않는다
6. **가격은 `saleInfo.retailPrice`, 통화가 `KRW`일 때만.** 0원이면 무료로 단정하지 않고 표시하지 않는다

**어디에 무엇을 보여주는가**
- **바코드 스캔 → 곧바로 그 책의 상세**(모든 칸). 주된 경로다
- **앱 상세는 칸마다 따로 받아 먼저 온 칸부터 그린다.** 가장 느린 제공자(Google, 실측 최대 1.7초)가 화면 전체를 붙잡지 않게 한다
- **제목 검색 목록**은 10권씩, 스크롤하면 다음 10권. 목록에는 표지·제목·새 책 판매 상태(검색 응답에 이미 있어 추가 호출 0)를 먼저 띄운다. **"내 도서관에 있음"은 화면에 보이는 책만 늦게 채운다** — 정보나루 한도가 6-7절 기준에 못 미치면 목록에서는 빼고 상세에서만 보여준다
- **공개 웹 책 페이지**에는 빌리기 칸이 없다. 로그인하지 않은 사람의 "내 도서관"을 모르고, 방문자가 지역을 고르게 하면 봇이 지역×ISBN 조합으로 한도를 태운다. 대신 "앱에서 내 동네 도서관 확인하기"로 안내한다
- **공개 페이지는 어떤 제공자도 동기로 부르지 않는다.** 캐시에 있으면 기준 시각과 함께 보여주고, 없거나 오래됐으면 그 칸은 "확인 불가"와 링크만 보여주고 갱신은 백그라운드 큐에 넣는다. 봇·카톡 미리보기가 제공자 응답을 기다리지 않고, 봇이 페이지를 훑어도 호출은 백그라운드 상한 안에서만 일어난다

### 왜 죽지 않는가 (유입 구조)

불특정 다수 공개 서비스는 "첫 사용자를 어디서 데려오는가"에서 죽는다. 이 서비스는 유입이 제품에 내장되어 있다.

- **자랑 유입** — 사용자가 자기 서재 링크를 카톡·인스타에 퍼뜨린다. 받은 사람은 앱 설치 없이 브라우저로 본다
- **검색 유입** — `/book/{isbn}` 페이지가 쌓이며 검색엔진에 걸린다. 책이 늘수록 유입도 는다. 시간이 자산이 되는 유일한 경로

앱스토어 검색에만 의존하면 신규 앱이 발견될 확률은 사실상 0이다. **공개 웹페이지가 없으면 목표 자체가 무너진다.**

## 3. 기술 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 앱 | **Flutter (Dart)** | iOS(본인 폰) 필수. 새 언어·새 런타임이라 "폭을 넓힌다"에 부합. React 습관을 못 쓰니 오히려 프론트 관성에서 벗어난다 |
| 서버 | **Spring Boot (Java 21)** | `spring-study`에서 배운 것을 백지에서 다시 짠다. Flutter로 이미 새 것 하나를 들고 가므로 리스크를 분산 |
| 공개 웹 | **서버 렌더링 HTML** | 열람 전용이라 SPA가 필요 없다. 프론트 프레임워크를 통째로 안 들인다 |
| DB | PostgreSQL | `spring-study`와 동일 |
| 외부 | 카카오 책 검색, 도서관 정보나루, Google Books | 공식으로 개인 개발자에게 열려 있다. 셋 다 실측했다(`docs/notes/providers.md`) |
| 인프라 | OCI 무료 티어 + Nginx + certbot | `spring-study`와 동일. 여기서 아낀 시간을 Flutter에 쓴다 |

### 공개 웹페이지를 Flutter Web으로 만들지 않는 이유

기술적으로는 가능하지만 이 페이지의 목적을 파괴한다.

1. **카톡 공유 미리보기가 안 뜬다 (결정적)** — 미리보기 카드는 봇이 HTML `<meta>` 태그를 읽어 만든다. 봇은 자바스크립트를 실행하지 않는다. Flutter Web은 봇 눈에 빈 껍데기다. **자랑 유입이 통째로 죽는다**
2. **검색에 안 걸린다** — 텍스트를 캔버스에 그리므로 검색엔진이 내용을 못 읽는다. 검색 유입도 죽는다
3. **무겁다** — 표지 몇 장 보려고 수 MB를 내려받는다. 카톡에서 눌렀는데 흰 화면이면 닫는다

판단 기준: **사람이 아닌 것(검색봇, 카톡 봇)이 읽는 화면은 서버가 완성된 HTML을 줘야 한다.**

### 의도적으로 배제한 것
- **Kotlin 네이티브 안드로이드** — 본인 폰이 iPhone이라 자기가 못 쓰는 앱이 된다
- **웹 + PWA만으로 끝내기** — iOS Safari의 카메라·푸시 제약. "서점에서 꺼내 찍는" 경험이 약해져 차별화가 흐려진다
- **Kakao 로그인** — iOS 전용이고 Apple 로그인은 심사 요구사항이라 어차피 필수. 2종을 붙일 시간이 없다
- **스크래핑·비공식 API로 서점 데이터 가져오기** — 공식 API를 닫은 곳의 데이터를 자동 수집하면 약관 위반이고, 불특정 다수 서비스에서는 법적 위험이 된다. HTML이 바뀌면 조용히 틀리고, 서버 IP 하나가 막히면 전원이 막힌다

## 4. MVP 경계

병행 프로젝트의 사망 원인 1위는 범위다. **"찍는다 → 기록된다 → 어떻게 읽을지 보인다 → 링크가 생긴다"** 한 줄기만 남긴다.

### 넣는 것
1. **Apple 로그인**과 **계정 삭제** — Apple은 계정을 만들 수 있는 앱에 앱 안 계정 삭제를 요구한다. 삭제 시 Apple 로그인 토큰도 철회한다
2. **바코드 스캔 → ISBN → 책 정보 자동 채움**
3. **제목 검색 → 책 선택 → 기록** — 손에 없는 책도 기록해야 한다. 이게 없으면 `읽고싶다` 상태가 죽고, 위시리스트 감시로 확장할 길도 막힌다
4. **기록과 편집** — 상태(읽고싶다/읽는중/읽음), 별점, 한줄평, 공개 여부
5. **읽을 수단 한 화면** (2-1절) — 새 책 판매 상태, 모든 구매처·중고·전자책 링크, Google Play 가격(같은 책 확인)
6. **도서관 등록(최대 3곳)과 대출 가능 여부** — 정보나루. "어떻게 읽을까"의 기반이라 후순위에서 올렸다. 지역으로 도서관을 찾아 등록한다
7. **공개 서재 웹페이지** — 비로그인 열람, 검색엔진이 읽어감
8. **공유 흐름** — 공유를 누르면 일괄 공개 전환을 제안 (7-4절)

### 지금은 없는 것
추천, 팔로우·피드, 통계 대시보드, 문장 수집(OCR), 위시리스트 가격 감시, **서점별 재고, 중고 가격, 전자도서관, 오디오북.**

서점별 재고와 중고 가격은 공식으로 얻을 길이 없다(6장). 전자도서관은 지자체마다 시스템이 달라 통합 API가 없다.

위시리스트 감시는 아깝지만 **감시할 목록이 비어 있는 상태에서 만들면 아무 일도 안 일어난다.** 서재가 먼저 차야 의미가 생긴다.

### 완료 기준
서점에 서서 폰으로 책을 찍으면 동네 도서관에 있는지와 어디서 살 수 있는지가 보이고, 집에 와서 그 서재 링크를 카톡으로 보낼 수 있다.

**정보나루를 뒤로 미룬 경우(9장 버리는 순서 3)의 완료 기준:** 서점에 서서 폰으로 책을 찍으면 판매 상태와 모든 구매처 링크가 보이고, 집에 와서 그 서재 링크를 카톡으로 보낼 수 있다.

## 5. 도메인 모델

핵심 원칙: **내 데이터와 남의 데이터를 섞지 않는다.**

```
Member              내 계정. slug(공개 URL), 서재 공개 여부, 기본 visibility
  ├─ ReadingRecord  ★ 절대 잃으면 안 되는 것
  │     status(WANT/READING/DONE), rating, review,
  │     startedAt, finishedAt, visibility
  └─ MemberLibrary  내가 등록한 동네 도서관 (최대 3곳). 공개 경로에 절대 나오지 않는다

Book                남의 데이터. isbn13이 식별자. 표지·제목·저자·출판사
                    제공자 응답의 캐시일 뿐이다. 쪽수는 nullable — 카카오에도 정보나루에도 없다(실측)

SaleSnapshot        남의 데이터. 정가·판매가(없으면 null)·판매 상태(판매 중/주문 후 발송/판매 정보 없음)
EbookOffer          남의 데이터. 같은 책 확인 결과·가격·Google Books 링크. "같은 책 없음"도 저장한다
Library             남의 데이터. 도서관 코드·이름·지역 (필드는 가정)
LibraryHolding      남의 데이터. (도서관, ISBN)마다 소장·대출 가능 여부와 기준 시각(전날)
```

캐시 기간은 6-5절 한 곳에만 둔다.

**ISBN 정규화.** 모든 테이블은 13자리 ISBN으로 저장한다. 카카오 `isbn`은 `"10자리 13자리"`를 공백으로 이은 문자열이고, 13자리만 오거나 앞에 공백이 붙기도 한다(실측). 공백으로 나눠 13자리가 있으면 그것을, 없으면 10자리를 13자리로 바꿔 쓴다. 체크섬이 틀리면 버린다. 같은 책이 두 번 저장되지 않게 하는 것이 목적이다.

경계를 이렇게 그은 이유:

- **`ReadingRecord`는 `Book` 없이도 존재해야 한다.** 제공자에 없는 책(절판·독립출판·해외서)을 찍었을 때 "등록 실패"가 뜨면 안 된다. ISBN만으로 기록이 먼저 생기고 책 정보는 나중에 붙는다
- **`SaleSnapshot`·`EbookOffer`·`LibraryHolding`은 틀려도 되는 데이터다.** 대신 화면에 기준 시각을 반드시 같이 보여준다. 정확한 척하면 사용자가 헛걸음한다
- **제공자가 죽었을 때의 모습이 이 모델의 시험대다.** 알라딘은 실제로 죽었다. 표지가 회색 박스가 되고 가격에 "확인 불가"가 뜨더라도 **서재와 기록은 멀쩡해야 한다**

## 6. 외부 제공자 전략과 캐시

### 6-1. 제공자 선정 기준

2026년 여름, 알라딘 OpenAPI와 네이버 책·쇼핑 검색이 잇달아 닫혔다(`docs/notes/providers.md`). 상업 서점·포털의 책 데이터 API는 닫히는 추세로 본다.

**지금 구조의 의존을 정직하게 적는다.** 책 정보·제목 검색·새 책 상태는 **카카오 하나에 의존한다.** 공공 데이터(정보나루)가 맡는 것은 빌리기 칸이다. 카카오가 닫히면 신규 스캔은 책 정보 없는 ISBN 기록만 남고 제목 검색은 멈춘다(기존 기록과 이미 아는 책은 멀쩡하다). 그래서 **정보나루의 도서 검색·ISBN 조회를 W1~W3 실측 항목에 넣고, 쓸 만하면 `BookCatalog`의 대체 구현으로 둔다.**

제공자를 넣거나 바꿀 때 아래를 모두 본다. **실측 결과는 `docs/notes/providers.md`에 남긴다** — 문서가 아니라 실제 응답이 기준이다.

1. **공식적이고 개인이 신청할 수 있다** — 우회·스크래핑은 하지 않는다
2. **ISBN 조회와 제목 검색**을 지원한다(책 정보 제공자의 경우)
3. **한국 책 수록률** — 국내 신간·구간·독립출판·해외서로 실측한다
4. **가격·상태 제공 여부**
5. **일일 한도와 초기화 시간대**
6. **약관** — 캐시 보관 기간, 출처 표시 의무, 검색엔진에 노출되는 공개 웹에 게재해도 되는지, 유료화 제한. **세 제공자 모두 W1에 확인해 `providers.md`에 적는다** (지금은 Google의 유료화 금지·표시 의무만 확인됨)
7. **대체 가능성** — 한 곳이 닫혀도 구현 하나만 바꾸면 되는가

### 6-2. 제공자 구조

화면의 칸마다 인터페이스를 두고, 제공자는 그 뒤의 구현 하나다. **제공자를 바꾸면 구현 하나만 갈아 끼운다.** 화면과 서비스는 인터페이스만 안다.

| 칸 | 인터페이스 | 지금의 구현 | 대체 후보 | 죽으면 |
|---|---|---|---|---|
| 책 정보·검색·새 책 상태 | `BookCatalog` | 카카오 | 정보나루 `srchBooks?title=`·`srchDtlList` (실측으로 쓸 만함 확인. 가격·판매 상태는 없다) | 로컬 `Book`만. 새 검색은 "잠시 후 다시", 새 책 칸은 "가격 확인 불가" |
| 빌리기 | `LibraryAvailability` | 정보나루 | — | "확인 불가" |
| 전자책 가격 | `EbookPricing` | Google Books | — | 숫자 없이 링크만 |
| 서점 링크 | `StoreLinks` | 설정 파일(API 없음) | — | 죽지 않는다 |

**예산·쿨다운·타임아웃은 제공자마다 따로 둔다.** 카카오가 느려져도 정보나루 칸은 영향을 받지 않는다. 타임아웃은 실측 최대 응답 시간에서 정한다.

| 제공자 | 실측 응답 | connect / read |
|---|---|---|
| 카카오 | 55~204ms | 1초 / 2초 |
| Google Books | 0.5~1.7초 | 1초 / 3초 |
| 정보나루 | 실측 전 | 실측 후 같은 방식으로 |

### 6-3. 호출 예산

**제공자별 상한** — 호출 카운터는 `(날짜, 제공자)` 단위이고, 날짜는 **그 제공자의 한도 초기화 시간대**를 따른다.

| 제공자 | 공식 한도 | 초기화 기준 | 우리 상한 (90%) | 백그라운드 상한 (60%) |
|---|---|---|---|---|
| 카카오 | 일 30,000 (Daum 검색 합산) | KST 자정 (가정) | 27,000 | 18,000 |
| 정보나루 | **일 500** (서버 IP 미등록 시. 등록하면 상향되지만 값은 공개되지 않음) | KST 자정 (가정) | 450 | 300 |
| Google Books | 콘솔 할당량 (W1 확인) | 태평양 시간 자정 (가정) | 같은 규칙 | 같은 규칙 |

백그라운드는 사람이 기다리지 않는 호출이다 — 공개 페이지 갱신 큐, 백필, 도서관 목록 동기화. **봇이 공개 페이지를 훑어도 백그라운드 상한에서 멈추고, 나머지는 앱 사용자 몫으로 남는다.** 한도가 커진 것(알라딘 5,000 → 카카오 30,000)은 이 구조를 없앨 이유가 아니다 — 봇의 호출량은 한도와 무관하다.

**사용자별 상한** — 공개 페이지만 막으면 로그인 사용자나 앱이 아닌 스크립트가 검색·ISBN 조회로 한도를 태울 수 있다. 서로 다른 검색어·없는 ISBN은 캐시에 걸리지 않는다.

- **검색·ISBN 조회·빌리기 API는 인증 필수**다
- **사용자별 일일 제공자 호출 상한**을 둔다(초기값 300회). 캐시에 걸린 요청은 세지 않고, **캐시에 걸리지 않은 요청은 결과가 비어도 센다.** 상한을 넘으면 그 사용자만 "잠시 후 다시"다
- **빌리기 조회의 도서관은 서버가 `MemberLibrary`에서만 꺼낸다.** 요청 파라미터로 도서관 코드를 받지 않는다 — 받으면 2-1절이 막은 "지역×ISBN 훑기"가 로그인 뒤로 옮겨갈 뿐이다
- **등록 도서관 변경은 하루 3회까지**다. 도서관을 바꿔 끼우며 훑는 것을 막는다

### 6-4. 3층 방어

**가장 싼 곳에서 가장 먼저 막는다.**

1. **앱에서 디바운스** — 입력이 400ms 멈춘 뒤, 2글자 이상일 때만 호출. 키 입력 9번이 호출 1번이 된다
2. **서버에서 검색어 캐시** — 검색어를 정규화해 키로 쓰고 결과를 24시간 저장한다. 같은 검색어는 24시간에 한 번만 제공자에게 간다. **서버도 2글자 규칙을 검사한다** — 구버전 앱이나 앱이 아닌 클라이언트는 디바운스를 지키지 않는다
3. **로컬 `Book` 우선** — 누군가 한 번 스캔·검색한 책은 이미 우리 DB에 있다. **사용자가 늘수록 외부 의존이 저절로 줄어든다**

검색어 정규화 규칙(공백·대소문자·자모 처리)은 캐시 적중률을 좌우하며 정답이 하나가 아니다. 구현 시 직접 정한다.

### 6-5. 캐시는 데이터의 성격대로

캐시 기간은 이 표 한 곳에서만 정한다.

| 데이터 | 캐시 | 이유 |
|---|---|---|
| 책 정보 (`Book`) | 영구 (로컬 우선) | 표지·제목·저자는 안 바뀐다 |
| 새 책 판매 상태·가격 (`SaleSnapshot`) | 6시간 | 자주 바뀐다 |
| 도서관 소장·대출 (`LibraryHolding`) | **조회한 날 다음 날 00:00 KST까지** | 정보나루가 원래 전날 대출 상태를 준다(실측·공지로 확인). 그날 안에 다시 물어도 같은 값이다 |
| 도서관 목록 (`Library`) | 7일 | 도서관은 거의 안 바뀐다 |
| 전자책 가격 (`EbookOffer`) | 24시간, "같은 책 없음"도 캐시 | 호출이 느리다(0.5~1.7초) |
| 검색어 → 결과 | 24시간 | |

### 6-6. 한도 소진·장애 시의 모습

한도를 넘기거나 제공자가 죽어도 앱이 흰 화면이 되면 안 된다.

- 이미 아는 책: **정상 동작** (책 정보는 로컬, 상태는 기준 시각과 함께 옛 값)
- 새 검색만: "잠시 후 다시" 안내
- 해당 제공자의 칸만: "확인 불가". 다른 칸과 링크는 그대로
- 서재·기록·공개 페이지: **전부 멀쩡해야 한다**

### 6-7. 정보나루 실측 마감과 불합격 기준

**결정 (2026-10 실측 후):** 소장·대출 여부(전날 기준, 대출 가능/대출 중/미소장), 지역별 도서관, 소장 도서관 찾기는 모두 된다. 쪽수는 주지 않는다. **한도는 IP 미등록 시 하루 500건이고, 등록 후 한도는 공개되지 않았다.**
- **실사용 전까지:** 하루 500건(상한 450)으로 간다. **"내 도서관에 있음"은 상세 화면에서만** 보여준다(아래 표의 가운데 칸을 미리 적용). 본인·지인 단계에는 충분하다 — 도서관 3곳 기준 하루 150번의 상세 조회, 같은 도서관은 하루 캐시를 공유한다
- **다시 볼 시점:** 불특정 다수에게 공개하기 전(앱스토어 정식 출시 전), 또는 호출 카운터가 상한의 80% 경고를 내기 시작할 때. 그때 서버 IP를 등록하고 올라간 한도로 아래 표를 다시 적용한다
- 실측 기록: `docs/notes/providers.md`

아래는 실측 전에 세운 원래 기준이다.

정보나루는 빌리기 칸 전체가 기대는 제공자인데 아직 한 번도 호출하지 못했다. 한도가 작다는 사실을 앱 작업 중에 알면 고칠 시간이 없다. 그래서 마감과 기준을 미리 정한다.

**마감: W3 끝.** 그때까지 확인할 것 — 도서관별 소장·대출 가능 여부의 상태 값, 데이터 갱신 주기, 지역으로 도서관 찾기, 쪽수 제공 여부, 도서 검색·ISBN 조회(카카오 대체 후보), 일일 한도와 초기화 시각, 약관.

**호출량 계산** (캐시가 하나도 맞지 않는다고 보는 보수적 추정. 등록 도서관 3곳, 활성 사용자 100명):
- 상세 1회 = 도서관 수 = 3회. 사용자당 하루 상세 10회 → 100명 × 30 = **3,000회**
- 목록 1페이지 = 10권 × 3곳 = 30회. 사용자당 하루 3페이지 → 100명 × 90 = **9,000회**

**기준.** 정보나루는 공개 페이지에서 부르지 않으므로 백그라운드 호출은 도서관 목록 동기화(주 1회)뿐이라 거의 0이다. 그래서 위 호출량이 **우리 상한(한도의 90%)에 1.5배 여유를 두고** 들어가는지를 본다.
- 목록 + 상세: (3,000 + 9,000) × 1.5 ÷ 0.9 = **20,000**
- 상세만: 3,000 × 1.5 ÷ 0.9 = **5,000**

| 실측 결과 | 결정 |
|---|---|
| 한도 ≥ 20,000/일 | 2-1절 그대로 (목록 + 상세) |
| 5,000 ≤ 한도 < 20,000 | **목록에서 뺀다**(버리는 순서 2를 미리 실행). 상세에서만 보여준다 |
| 한도 < 5,000, 대출 가능 여부를 주지 않음, 또는 W3 끝까지 승인이 나지 않음 | **버리는 순서 3** — 정보나루를 TestFlight 이후로 미루고 4장의 축소판 완료 기준으로 간다 |

## 7. 인증과 공개 경계

인증이 필요한 세계와 아예 없는 세계가 한 서버에 공존한다. 경계를 어디에 긋느냐가 보안의 전부다.

### 7-1. 인증

```
[앱]        Apple 로그인 → 받은 토큰을 서버로 전달
                 ↓
            서버가 Apple 공개키로 서명을 직접 검증
                 ↓
            우리 JWT 발급 (Access 짧게 + Refresh는 iOS Keychain)

[브라우저]  인증 없음
```

**네이티브 앱의 소셜 로그인은 웹 OAuth2와 다르다.** 웹은 브라우저가 카카오로 갔다가 인가 코드를 들고 우리 서버로 리다이렉트된다. 앱에는 **리다이렉트가 없다.** SDK가 앱 안에서 로그인을 끝내고 토큰을 앱 손에 쥐여주면 앱이 그걸 서버로 보낸다.

여기에 함정이 있다. **앱이 보낸 토큰을 그냥 믿으면 누구나 남의 계정이 된다.** 공격자가 아무 식별자나 넣어 보내면 끝이다. 반드시 서버가 Apple 공개키로 서명을 검증해야 한다. 웹 OAuth2에서 스프링이 대신 해주던 일을 직접 한다.

### 7-2. 공개 경계 — 유출은 여기서 난다

공개 페이지는 인증이 없으니 인가 검사도 없다. 실수 한 번이 전체 유출이다.

가장 흔한 사고 경로는 "기존 조회 서비스를 재사용하고 공개 필터만 하나 추가"하다가 조건 한 줄을 빠뜨리는 것이다.

> **규칙: 공개 조회는 인증된 조회 코드를 절대 재사용하지 않는다.**
> 공개용 읽기 전용 쿼리를 따로 두고, 그 쿼리는 애초에 비공개 데이터를 **못 가져오게** 작성한다.

"필터를 거는" 것이 아니라 "가져올 수 없는" 구조로 만든다. 사람이 매번 기억해야 하는 방어는 언젠가 실패한다.

추가로:
- **`record id`를 공개 URL에 노출하지 않는다.** id가 나가면 번호를 올려가며 남의 기록을 훑는 시도가 들어온다. 공개 조회는 `slug`로만
- **비공개 서재의 slug는 404.** "비공개입니다" 페이지는 "이 사람이 가입했다"를 누설한다
- **탈퇴 시 공개 페이지는 즉시 사라진다**
- **공개 책 페이지는 DB에 있는 책만 보여준다.** 없는 ISBN이면 제공자를 부르지 않고 404다 — 부르면 ISBN을 올려가며 요청하는 것만으로 한도가 바닥난다
- **공개 책 페이지와 사이트맵은 공개된 기록이 있는 책만 다룬다.** 열린 서재에 PUBLIC·RATING_ONLY 기록이 하나라도 있어야 한다. 백필은 공개 여부와 상관없이 모든 기록의 책을 채우므로, book 행이 있다는 것만으로 페이지를 열면 비공개로 둔 책이 드러난다(2026-09-30 최종 리뷰에서 발견)
- **책 정보가 아직 없는 공개 기록**은 공개 서재에 회색 표지와 ISBN으로 보여주고 **책 페이지 링크를 걸지 않는다.** 걸면 위 규칙 때문에 404로 이어진다
- **서재를 닫은 사람의 기록은 책 페이지에 어떤 형태로도 싣지 않는다.** 이름 링크가 404로 이어지면서 "가입했고 서재를 닫았다"를 누설하기 때문이다. 서재 스위치와 기록의 visibility가 둘 다 열려 있어야 공개다

### 7-3. visibility

기본값은 **비공개**다. 공개 경로는 사고 파장이 크므로, 초기 버그가 나도 아무것도 새지 않는 쪽을 기본으로 둔다.

| 값 | 공개 서재에서 | 책 페이지에서 | 의미 |
|---|---|---|---|
| `PUBLIC` | 표지·별점·한줄평 | 이름·별점·한줄평이 실린다 | 다 보여준다 |
| `RATING_ONLY` | 표지·별점만 | **아무것도 실리지 않는다** (이름·별점 포함) | 읽은 건 알리되 감상은 내 것 |
| `PRIVATE` (기본) | 아예 없음 | 아무것도 실리지 않는다 | 읽었다는 사실조차 숨긴다 |

`Member` 레벨 스위치가 별도로 필요하다. 기록 단위 설정만으로는 "서재 페이지 자체를 닫기"를 표현할 수 없다.

**`RATING_ONLY`가 가장 까다롭다.** 같은 행을 가져오되 일부 컬럼만 노출해야 한다. 엔티티를 그대로 내보내면 한줄평이 딸려 나가므로, **공개용 응답 타입에는 한줄평 필드가 아예 없어야 한다.** 필드가 없으면 실수로 채울 수 없다.

**공개 페이지의 집계 숫자는 공개 기록만 센다.** 서재 페이지와 책 페이지 모두 같다. "올해 32권"에 비공개 책을 포함하면 표지는 6장인데 32권이라 적힌 페이지가 비공개 기록 개수를 누설한다. MVP의 책 페이지에는 "N명이 읽음" 같은 집계를 두지 않는다. 나중에 둔다면 열린 서재의 `PUBLIC` 기록만 센다.

`MemberLibrary`(내가 등록한 도서관)는 **공개 경로에 절대 나오지 않는다.** 동네 도서관 세 곳은 사는 곳을 좁힌다.

### 7-4. 기본 비공개와 유입의 충돌

기본 비공개면 아무도 공유하지 않아 유입 구조가 작동하지 않는다. 기본값을 바꾸지 않고 회수한다 — **공개를 "설정에서 켜는 것"이 아니라 "공유를 누르는 순간의 흐름"으로 만든다.**

```
공유하기 탭
   ↓
"이 서재는 지금 비공개예요. 링크를 열려면 공개해야 합니다."
[ 읽은 책 32권 모두 공개 ]  [ 별점만 공개 ]  [ 취소 ]
   ↓
일괄 전환 → 서재 스위치 켬 → 링크 생성
```

일괄 전환의 범위는 한 가지로 정한다.

| | 바뀌는가 |
|---|---|
| **읽음(`DONE`) 기록** | 선택에 따라 `PUBLIC` 또는 `RATING_ONLY`로 바뀐다 |
| 읽고 싶다(`WANT`)·읽는 중(`READING`) 기록 | **바뀌지 않는다** |
| 앞으로 만들 기록의 기본 visibility(`Member` 기본값) | **바뀌지 않는다** — 여전히 비공개 |
| 서재 스위치 | 켜진다 |

설정 화면에 묻힌 스위치는 아무도 켜지 않지만, 행동의 길목에 놓인 질문은 대부분 "예"를 받는다.

### 7-5. 구글은 기억한다

공개했다가 비공개로 돌린 서재는 우리 DB에서 사라져도 검색 캐시에 한동안 남는다. 사용자는 즉시 지워진 줄 안다. **비공개 전환 시 "검색 결과에서 사라지는 데 며칠 걸릴 수 있다"고 알려주는 것까지가 기능이다.**

## 8. 배포와 운영

배포 대상이 둘이라는 점이 `spring-study`와 결정적으로 다르다.

| | 서버 | 앱 |
|---|---|---|
| 배포 주기 | 즉시 | 심사 대기 (수일) |
| 롤백 | 즉시 | 불가능 |
| 사용자 버전 | 항상 최신 | 구버전이 영원히 남는다 |

**앱은 롤백이 안 되고 옛 버전 사용자가 계속 남는다.** 서버가 API를 바꾸면 구버전 앱이 그날로 죽는다. 대응은 둘이면 충분하다.

- **API 응답에서 필드를 절대 삭제하지 않는다** (추가만 허용)
- **강제 업데이트 스위치** — 서버가 "이 버전 미만은 업데이트 필요"를 내려주는 엔드포인트 하나. 진짜 깨지는 변경이 필요할 때의 유일한 탈출구

같은 이유로 **제공자를 바꿔도 앱 API는 바뀌지 않아야 한다.** 앱은 "빌리기/새 책/전자책" 칸의 모양만 알고, 그 뒤의 제공자 이름은 모른다.

인프라는 `spring-study`와 같은 OCI 무료 티어에 얹는다. Postgres 컨테이너 하나 추가, 도메인 하나 신규.

제공자별 운영 규칙:
- **Google Books API 키는 서버 IP만 허용**하도록 제한한다(실측 중에는 제한 없음)
- **Google Books 결과는 요청 서버의 위치에 따라 달라진다.** 서버를 확보하는 대로(W1) 도쿄 서버에서 `country=KR`로 원화 가격이 나오는지 curl로 확인한다. 안 나오면 Google Play 가격 칸을 버린다(버리는 순서 1) — 11월에 만들고 나서 알면 늦다

### 테스트 우선순위
1. **공개 경계 테스트** — 비공개 기록이 공개 페이지·책 페이지·집계 숫자 어디에도 나오지 않는지. `MemberLibrary`가 공개 경로에 나오지 않는지. **빠짐없이.** 사고 나면 되돌릴 수 없는 유일한 영역. **공개 페이지를 만드는 주(W4)에 골격을 함께 쓴다** — W5부터 공개 웹이 떠 있고 W8부터 실제 비공개 기록이 쌓이므로, 테스트 없이 노출되는 기간을 두지 않는다
2. **외부 제공자 실패** — 제공자마다, 죽거나 한도가 바닥났을 때 **그 칸만** "확인 불가"가 되고 나머지는 멀쩡한지 (WireMock)
3. **같은 책 확인** — 실측의 오탐(중국어판·타밀어판·토지 7권)이 걸러지는지, 권 표시·저자 규칙
4. **사용자별 상한** — 스크립트 하나가 한도를 태우지 못하는지
5. 나머지는 여유 될 때

### 관측
하나만 있으면 된다 — **오늘 제공자별로 몇 번 불렀는가.** 상한에 닿으면 그 칸이 반쯤 죽는데, 사용자 항의로 알게 되면 늦다.

## 9. 일정

총 예산: **주 4~5시간 × 14주 = 56~70시간.** 이 중 Flutter 학습에 15~20시간, iOS 첫 배포 절차(인증서·프로비저닝·스크린샷·개인정보처리방침·심사)에 10시간 이상이 나간다. 실제 구현에 쓸 수 있는 것은 **26~40시간**이다.

비용: **Apple Developer Program 연 $99** (가입 승인에 며칠).

### "배포"의 정의를 나눈다

앱스토어 정식 출시를 연말 목표로 잡으면 심사 반려 한 번에 계획 전체가 무너진다.

| | 연말 목표 |
|---|---|
| **웹 (공개 서재·책 페이지)** | **정식 공개.** 심사가 없어 내 의지로 배포된다. 검색 유입도 이때부터 쌓인다 |
| **Flutter 앱** | **TestFlight.** 심사가 가볍고 링크로 초대 가능. 나와 지인이 쓰면서 다듬는다 |

앱스토어 정식 출시는 2027년 1~2월로 미룬다.

### 14주

정보나루가 MVP로 올라오고 Google Books가 더해져 범위가 늘었다. **원래 W14 여유분을 쓰고, 정보나루 서버 작업은 Flutter 앞으로 당긴다** — 실측 결과에 따라 모델과 UI를 바꿀 시간을 남기기 위해서다.

```
10월  W1  준비 — 제공자 실측 마무리(정보나루 승인 시, Google 할당량·language 필드, 세 제공자 약관),
          서버 확보 후 도쿄에서 Google country=KR 확인, Apple Developer 가입, 도메인, 스켈레톤
      W2  백엔드 코어 — 전체 스키마(Book / ReadingRecord / SaleSnapshot / EbookOffer / Library /
          MemberLibrary / LibraryHolding), 제공자별 예산 카운터
      W3  카카오 연동 — 검색·ISBN + 3층 캐시 + ISBN 정규화.  ★ 정보나루 실측 마감 (6-7절)
      W4  공개 웹페이지 — 서재, 책 페이지(새 책 상태 + 링크), OG 태그, 갱신 큐 + ★ 공개 경계 테스트 골격
11월  W5  ★ 웹 배포 — 이 시점에 "살아있는 서비스"가 생긴다
      W6  인증 — Apple 토큰 검증, JWT, 사용자별 호출 상한, 계정 삭제(서버, Apple 토큰 철회)
      W7  정보나루 서버 — 도서관 목록 동기화, 지역으로 찾기, 소장·대출 조회, 빌리기 API
      W8  Flutter — 로그인, 서재 목록, 기록 편집(별점·한줄평·공개 여부)
      W9  Flutter — 제목 검색·바코드 스캔 → 상세(읽을 수단 한 화면, 칸별 점진 로딩)
12월  W10 Flutter — 도서관 등록, 상세의 빌리기 칸, 목록의 "내 도서관에 있음", 계정 삭제 UI
      W11 공유 흐름(일괄 공개 전환) + Google Play 전자책 가격(같은 책 확인)
      W12 공개 경계 테스트 보강
      W13 TestFlight 배포
      W14 실사용 → 버그
```

세 가지가 이 일정의 뼈대다.

- **W1의 Apple Developer 가입.** 코드와 무관하지만 리드타임이 있다. 12월로 밀리면 TestFlight 자체가 불가능하다
- **W3의 정보나루 실측 마감.** 빌리기 칸의 운명이 여기서 정해진다(6-7절)
- **W5의 웹 선배포.** 앱이 늦어지거나 Flutter에서 막혀도 11월 초부터 배포된 서비스가 존재한다. **각 단계가 그 자체로 배포 가능하도록** 순서를 짰다

Flutter 주차(W8~W10)가 원래보다 빽빽하다. Flutter 학습이 밀리면 아래 순서대로 버린다.

### 밀리면 버리는 순서

여유분이 없으므로 미리 정해 둔다.

1. **Google Play 전자책 가격** — 링크는 남아 화면이 비지 않는다
2. **검색 목록의 "내 도서관에 있음" 늦은 표시** — 상세에서만 보여준다
3. **정보나루 전체를 TestFlight 이후로** — 4장의 축소판 완료 기준으로 간다. 가능한 한 끝까지 지킨다

**공개 경계 테스트(W4 골격, W12 보강)와 계정 삭제는 버리지 않는다.** 앞의 것은 되돌릴 수 없는 유일한 영역이고, 뒤의 것은 없으면 심사를 통과하지 못한다.
